# M3.9 — Poker 迁移与「结果窗口」钩子

- **基线**：`38f724b`（M3.8 完成）
- **范围**：迁移 Poker；新增一个契约钩子（`decisionReadyAt`）
- **结论**：8 款游戏全部迁完；Poker 房间从 **1,227 行降到 112 行**，既有 14 个用例断言不变

## 1. 结论

Poker 是这轮最大的一块，也是唯一**必须新增钩子**的一款。原因不在规则，而在一个平台语义：

> 每一手结束后，桌面要把结果展示五秒，这期间任何人不该收到新的合法动作，`wait_for_turn` 也不该立刻返回。

这段逻辑原来藏在 `PokerRoom.agentDecisionReadyAt()` 里——一个平台钩子，插件契约没有对应项。迁移时补进契约：

```ts
decisionReadyAt?(state: TState): number;
```

平台侧的 `agentDecisionReadyAt()` 改为"问插件"，其余七款游戏不实现，返回 0（立即就绪），行为不变。

## 2. 迁移后的边界

```text
apps/workers/src/games/poker/table.ts   938 行  下注状态机（原房间逻辑整体迁入）
apps/workers/src/games/poker/plugin.ts  347 行  契约装配、动作分派、投影、超时策略
apps/workers/src/durable-objects/PokerRoom.ts  112 行  平台胶水
```

合计 1,397 行，原房间 1,227 行——多出的部分是注释、类型与效应队列的接线。

## 3. 三个实现决策

**① 用「持有 state 的牌桌对象」而不是「state 作为参数的纯函数」。** 房间里有约六十个互相调用的私有方法（`afterAction → advanceStreet → runoutAndShowdown → showdown → awardPot → finishHand`），全部改成显式传参会产生几百处机械改动，也更容易出错。`PokerTable` 持有构造时传入的 state，方法体几乎逐行保留原文，只把 `this.gameState` 换成 `this.state`。

**② 平台调用全部变成效应。** 牌桌里原来会 `recordEvent`（事件）、`stopTimers`（时钟）、`saveState + broadcastProjected`（终局收尾）。现在统一压进 `effects` 队列，由 `applyAction` 一次性交给平台：审计事件、`stop_timers`、`match_ended`。牌桌因此不碰存储、套接字和定时器。

**③ 动作签名从 `Player` 换成 `playerId`。** 规则只需要身份，超时兜底（自动过牌/弃牌）也不需要伪造平台对象，只要一个 id。

## 4. 迁到一个坑：终局效应

第一版 `finishHand` 里我保留了 `stopTimers()` 与 `recordEvent("game_ended")`，只删掉了 `saveState`/`broadcast`，**漏了 `match_ended` 效应**。结果是：状态变成 `ended`，但对局没有归档——MCP 全链路用例在"等 R2 出现一份日志"这一步超时，而房间级用例全绿（它们不检查归档）。

这类"状态对了、效应漏了"的错误是本次迁移唯一需要警惕的模式：**凡是原来同时写了 state 又做了平台动作的地方，都要检查效应是否补齐**。

## 6. 剩余风险

1. **`PokerTable` 是有状态对象**。它在 `applyAction`、`projectState` 等入口各自被 new 一次，本身不缓存；但如果以后有人在方法里加缓存字段，投影路径就会读到过期数据。这条约束写在类注释里，但没有类型保护。
2. **异步的牌堆承诺哈希**。`shuffleDeck` 用 `void sha256Hex(...).then(...)` 回填 `deckCommitHash`，与迁移前完全一致；它意味着哈希可能在首次保存之后才落盘。这是既有行为，迁移没有改变，但值得记一笔。
3. **`mustEnd: false` 的逃生口**仍在全链路测试里（Poker 若在预算内打不完就只断言隐私与动作数）。当前策略下不会触发，但保留了这条路径。
4. **两处测试改为直接驱动 `PokerTable`**：断言没变，但测试与规则的耦合点从"房间子类"变成"牌桌对象"。这是正确方向，不过也让这两个文件不再覆盖房间接线。
