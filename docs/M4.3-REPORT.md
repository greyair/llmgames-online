## 1. 为什么先做一张共用的牌

两款游戏共享一副牌和"压过上一手"的判定，但合法牌型不同。把它们放进同一层，比复制两份近似代码更省事：

```text
apps/workers/src/games/cards/deck.ts    226 行  牌面编解码、rank 阶梯、洗牌、按 rank 选牌
apps/workers/src/games/cards/combo.ts   193 行  牌型识别 + 比较 + 描述
```

一个 `classify(cards, rules)` 认全 14 种牌型，`ComboRules` 决定这局游戏是否承认它：

| 旗标 | 跑得快 | 斗地主 |
| --- | --- | --- |
| `rocket`（双王） | ✗ | ✓ |
| `fourWithWings`（四带二 / 四带两对） | ✗ | ✓ |
| `minPairRun`（连对最短） | 2 | 3 |

比较只有一条规则：**火箭 > 炸弹 > 同型同张数比 key**。`beats()` 就这四行，所以"同型同张数、更大的主牌"不需要两套梯子。

牌面用文本 id：`S3`、`HT`、`DJ`，双王是 `j1` / `j2`。这里有一个真实踩坑：

> 双王最初写成 `SJ` / `BJ` 当标签，而 ♠J 的牌号正是 `SJ`。牌号解析器把黑桃 J 认成小王，一手正常的牌被判成"你手上没有小王"。MCP 全链路测试第一次跑就撞上了。现在王的**任何**表示都不带花色字母：id `j1`/`j2`，标签 `J1`/`J2`。

## 2. 跑得快的规则

48 张牌（无王、去掉 ♥2 ♣2 ♦2 与 ♠A）。三人局 48 张全发、每人 16；二人局每人 16、另 16 张作废。

```text
play_cards { cards: ["S3","H3"] }   出牌，支持只写 rank（"3 3"，服务端挑最小花色）
pass                                不要
```

三条容易写错的规则，都有测试：

1. **三张只能当最后一手**。领出阶段出裸三张要被拒；`pdkMoves` 也不把它列进提示，所以模型和超时兜底都不会撞墙。
2. **领出不能不要**。`turnActions` 在领出时只给 `play_cards`。
3. **一轮结束是"自上次出牌后其余人都不要"**。计数在每次出牌时清零，不是每轮清零——写成每轮清零会让第二个不要的人提前收下一轮。

超时策略：跟牌时按"不要"处理；领出时不能不要，于是服务端打出**手上最小的一手**（`pdkForcedPlay`），并发 `turn_timeout`。这是一个替玩家做的决定，但它是确定性的、最小的，而且总比让牌桌卡死好——报告里明确记一笔。

**投影是这一关的重点**。`hands` 与 `unused` 置 `undefined`（JSON 序列化时消失），换成：

```text
hand       自己的 16 张
handSeat   自己的座位
handCounts 每座剩余张数
```

牌桌本身（`trick` / `lastTrick` / `acts` / `passed`）是公开信息，因为它们正是玩家推理的依据。MCP 全链路里有一条断言：任何座位的视图都不含 `hands` 字段。

紧凑决策态给模型的是**算好的牌**而不是原始手牌：

```text
hand        "x2 (♠3 ♦3), x3 (♥5 ♣5 ♦5), (♠J) …"  按 rank 分组
hints       最多 28 条可直接发送的合法出牌
trick       "seat 1 played pair 8 (♠8 ♥8)"
canPass     领出时为 false
```

## 5. 前端

```text
apps/web/src/game-ui/Paodekuai.tsx   251 行  牌桌、手牌、选牌、出牌/不要
apps/web/src/game-ui/paodekuai.css   204 行  容器查询自适应

apps/web/src/interface/GameScene.tsx  96×64 场景（浅色牌桌 + 五张扇形牌）
```

版面从上到下是：对手剩牌胶囊 → 牌桌（桌面/上一轮赢家）→ 手牌 → 提示与按钮。

**一个刻意的取舍**：前端**不判断牌型**。选中任意张就能按"出牌"，判定和拒绝信息来自服务端。把 14 种牌型的分类器复制到浏览器，等于给"谁决定胜负"留了第二份会漂移的答案。代价是错误提示要等一次往返，收益是只有一份规则。

手牌布局在两种宽度下分别处理：

- 宽屏：一行不折行，放不下就横向滚动（隐藏滚动条）。16 张在 760px 内本来就放得下。
- ≤560px：换成两张更小的牌、允许折行成两排。手机上一行塞 16 张牌必然要么重叠到看不清点数、要么滚出屏幕——那都是玩家会忘记自己有哪些牌的理由。

## 6. 与来源的差异

| 项 | 来源 | 这里 | 原因 |
| --- | --- | --- | --- |
| 输入 | 文本 `"3 3 4 4"` | `{ cards: [...] }`，支持只写 rank | 平台要求可校验、可发现 |
| 座位数 | 2–3 | 2–3 | 同 |
| 洗牌 | `ctx.seed` 派生 | `randomInt` + Fisher–Yates（CSPRNG），结果进状态 | 可重现且不可预测 |
| 超时 | 无（靠客户端） | 跟牌=不要，领出=最小一手 | 无超时会让牌桌永久卡住 |
| 机器人 | `paodekuaiBot` | 未移植 | 平台不托管 bot |
| 春天计分 | 文本标注 | `game_ended.spring` 事件字段 | 平台没有跨局记分 |

## 9. 下一步：斗地主

牌型层已经就绪（`DOUDIZHU_COMBOS` 已开 火箭 / 四带二 / 连对 3 对，并有测试），剩下的是这款游戏真正特殊的两件事：

1. **叫分**：`bid` 阶段（1/2/3 或不要），最高者当地主、拿走 3 张底牌并先出；三家全不要则重发。这是一个新的阶段机，和跑得快的单阶段不同。
2. **一打二**：胜负不是单座位。要落地"地主 vs 农民"，`winnerTeam` 需要从 `"red" | "blue"` 扩成可扩展的字符串，`MatchResult` 的文案映射要跟着改——这是本阶段唯一一处**公开接口变更**，会在报告里单独记录。
