## 1. 结论

Codenames 已迁到插件契约。它是第一款**角色 + 私有信息 + 多人同队决策**的游戏，验证到两件事：

1. **既有钩子基本够用**：`projectState`（只让两位队长看钥匙）、`mayActNow`（整队 operative 同时可猜）、`onTurnTimeout` / `onMatchTimeout`、`youFields`（M3.5 新增，正好放下 `team` / `canSeeKey`）。
2. **只补了两个契约钩子**，都是 M3.3 能力文档里提前点名过的：`validateStart`（开局前校验角色配置）与 `onMemberRoleChanged`（玩家转旁观时清掉角色）。

规则从房间搬进 `games/codenames/`，房间 **812 → 288 行**；等价性由迁移前的金样本证明：**17 步 / 5 个房间 / 10 条拒绝 / 75 条事件 / 回放**，每步记录**四席 + 旁观**各自能读到什么。

**结果：迁移后与旧实现完全一致。**

## 2. 一个刻意的边界选择：大厅角色分配不进插件

`assign_codenames_role` / `reset_codenames_roles` / `randomize_codenames_roles` 留在房间适配器，原因不是省事：

- 选队是**席位变更**——它可以把旁观者提升为玩家（`promoteSpectatorToPlayer`），而 M3 设计 §3.2 把身份与席位划归平台层；
- 这类动作在 `saveState` 之前还要跑一次大厅归一化（新玩家入座即分配角色），这同样是持久化职责。

所以插件只负责**对局规则**：给线索、猜词、结束猜词、换手、两种超时、终局。适配器在 `handleGameAction` 里先拦下三个大厅动作，其余交给 `plugin.applyAction`。这条边界写进了两个文件的头注释，避免下一款角色型游戏照抄错位置。

## 3. 两个新增钩子

| 钩子 | 旧实现 | 为什么必须进契约 |
| --- | --- | --- |
| `validateStart?(state)` | `validateStartGame()` 覆写 | 开局前要拒绝"角色不全 / 两队队长数量不对 / 人数不平衡"，平台负责把 message + code 原样返回 |
| `onMemberRoleChanged?(state, playerId, role)` | `onRoomMemberRoleChanged()` 覆写 | 玩家转旁观时必须删掉其角色，否则残留的 `assignments` 会让他继续拿到钥匙 |

`BaseGameRoom` 的两个默认实现改为委托 `gameRules()`，与 M3.4.1 给 `projectStateFor` 定的规则一致：**平台默认实现只做转发，适配器不必重复写一遍**。

`onMatchTimeout` 顺带补了 `now` 参数（Codenames 要写活动日志时间戳）；Checkers/Reversi 的适配器改为传 `Date.now()`，行为不变。

## 4. 金样本

### 4.1 覆盖面

| 场景 | 房间 | 关键断言 |
| --- | --- | --- |
| 大厅 | A | 入座自动分配、显式指定、重置、随机化 |
| 线索阶段 | A | 队长（红）可给线索；非法线索四种（非队长 / 多词 / 计数越界 / 与可见词相同） |
| 猜词 | A | 猜中己方、猜中中立（换手）、猜错队（换手）、重复猜同一张、队长越权猜 |
| 结束猜词 | A | 至少猜过一次才允许停 |
| 回合超时 | A | 换手并重置计时 |
| 全员出局 | B | 红队 9 张全翻 → `all_agents_contacted` |
| 刺客 | C | 翻开刺客 → 对手胜 |
| 整局时钟 | D | 未完成盘面判和（`winner: "draw"`） |
| 无法开局 | E | 两队队长数量错误 → `CODENAMES_SPYMASTER_COUNT` |

每步记录：`p1`–`p4` 四席的 `you`、`board`（25 张，含是否揭晓与可见的归属）、完整 MCP 视图，外加一份旁观视图。

### 4.2 隐私核心

金样本里能直接读出这条规则：

```
start:clue   key p1(队长)=25  p3(operative)=0
guess:red-correct            p1=25         p3=1   ← 只多出被翻开的那张
end:all-agents（已结束）      p1=25         p3=25  ← 终局全场揭晓
```

### 4.3 确定性

生产随机性未改：`shuffleInPlace` / `randomInt` 仍是 CSPRNG。测试侧 `withSeededRandom()` 把 `crypto.getRandomValues` 填零，于是起始队、25 张牌序、钥匙布局、大厅洗牌全部固定。两次采集字节一致后再生成夹具。

采集时踩到一个**引用陷阱**并修掉：`clue` 与 `remaining` 最初按引用存进步骤，序列化时读到的是终局值（起始应 9/8，实际记成 6/7）。改为 `stripValue(...)` 复制后再记录，并加了注释。

## 6. 剩余风险

1. **`compactAgentDecisionState` 仍按 `gameType` 分支**（`packages/game-catalog/src/agent-state.ts`）。Codenames 的 `wait_for_turn` 仍走它，而 `agentFields` 已提供同样的字段；两份实现目前输出一致（金样本 + 既有测试双覆盖），但这是重复实现。**本轮没有收口**：插件的决定态钩子在 workers 侧，catalog 的压缩器在共享包里，收口需要新的依赖方向（让 MCP 层在压缩前先问插件），属于设计变更，不该塞进迁移里。
2. **大厅角色分配仍是适配器代码**。三款角色无关的游戏没有这个问题，但若将来出现第二款角色型游戏，应考虑把"选队"抽成平台能力（例如 `assignSeat` 通用动作），而不是复制 90 行。
3. **转旁观只在等待阶段可用**（平台限制）。对局中转旁观会怎样，本轮没有覆盖；`onMemberRoleChanged` 已被保存路径覆盖，但"对局中移出玩家"本身是平台既有约束。
4. **`rewatchView` 使用默认实现**（返回整份 state）。Codenames 的归档因此包含完整钥匙，这符合"回放全量揭示"的约定，但值得在归档文档里写清楚。
