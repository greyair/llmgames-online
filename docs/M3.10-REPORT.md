## 2. P1：Pokémon 的共享可变缓存

复审的判断是对的，我复现后确认它比报告描述的更容易触发——**不需要写入失败也会错位，只是要观察到错位才需要回滚**。

机制：`parseBattle()` 以快照字符串为键缓存一个 `Battle` 对象，而 `Battle` 是**可变**的。`applyAction` 里 `battle.choose()` 直接改它，`syncBattle` 只更新 `state.battleSnapshot`，没有更新缓存键。于是缓存里存着「S0 → 内容已经是 S1 的对象」。

平台确实有回滚路径：`saveAppliedAction()` 写失败时执行 `this.gameState = await storage.get("gameState")`（`BaseGameRoom.ts:2963`），把内存状态退回磁盘上的旧快照。此时 `parseBattle(S0)` 命中旧键，返回含未落盘行动的 S1——投影会显示一个从未被接受的行动。

修复：`syncBattle` 写完快照后同步移动缓存键（`rememberBattle`）。三个用例，前两个在修复前确实是红的（我把修复临时注释掉验证过）：

| 用例 | 修复前 | 修复后 |
| --- | --- | --- |
| 插件级：行动后回滚到旧快照，必须重新要牌 | 失败（`decision` 为 null） | 通过 |
| 房间级：注入写失败后读视图 | 失败 | 通过 |
| 两局持有不同快照，互不串扰 | 通过 | 通过 |

## 3. P2：决策态的归属

### 收口前

每款游戏的决策字段有两处定义：

```text
BaseGameRoom.buildAgentView   一个 switch，逐游戏挑字段 → 富视图（join_room 的返回）
game-catalog.agent-state.ts   一个 switch，逐游戏再挑一次并压缩 → 紧凑视图
```

两份清单意味着**漂移**：改了一处忘了另一处。而且新增游戏要改共享包才能让 MCP 可用。`battleship-state.ts`（183 行）甚至住在 `packages/game-catalog` 里，却只有 workers 用。

### 收口后

```text
packages/game-catalog/src/agent-state.ts   407 行  平台框架 + 通用助手，零游戏分支
apps/workers/src/games/<id>/agent.ts       19–153 行  每款游戏的紧凑字段
apps/workers/src/games/agent-decision.ts    26 行  按视图里的 type 找插件
```

契约新增一个钩子：

```ts
agentDecision?(view: ProjectionPart, legalActions: readonly string[]): WireObject;
```

- **框架归平台**：`series`、`gameType`、`status`、`phase`、`turnNumber`、两个时钟，以及**已过滤**的 `legalActions`（大厅类意图不算决策）。游戏不必重复"哪些动作不是决策"。
- **字段归游戏**：Connect 4 把数字棋盘压成数字行并算出仍可落子的列；Codenames 把牌面压成 `[index, word, revealed, affiliation]` 元组；Poker 去掉对手暗牌、把行动历史截到 24 条；Battleship 直接把 183 行网格构建搬到了自己的目录。
- **`agentFields` 保持不变**：`join_room` 返回的富视图形状未变，只把紧凑态换了归属。

### 兼容性证明

`check:ai-spec` 会重新生成公开文档并与仓库中的快照逐字比对：

```text
AI spec matches all 17 MCP tools, 8 game catalogs and 7 hosted Jev adapters.
```

也就是说对外发布的紧凑态示例**逐字节未变**。

### 第二个消费者

`packages/mcp-server`（可选的本地 stdio 桥接）也调用这个函数，但它在自己的包里，看不到插件。原来它拿一份 `ClientView` 套用按 `gameType` 的分支——本来就是近似。现在没有 `fields` 时，框架 + 该视图自己的字段原样透传，只去掉平台已经复述过的键（`players`、`roomMembers`、`turnState`、`type`、`gameTimeRemaining`、`series`）。这比"静默丢掉游戏字段"诚实，也不再需要共享包认识游戏。

## 4. 顺带删掉的死代码

- **`buildAgentView` 的第二个 switch**：八款游戏都已在注册表中，`rules.agentFields` 恒存在，这段分支永远走不到。删掉后，没有插件的游戏只拿平台框架——这正是它的语义。
- **`gameJourney` 的 `mustEnd: false`**：Poker 已经能用"有机会就全下"打到 `stack_out` 并归档（M3.9 已验证），逃生口留着只会被后人用来"打不完也放行"。现在所有脚本都必须真的结束并归档。

## 4.1 全量 E2E 抓到的回归

M3.6 之后每个阶段只跑本阶段相关的 spec，全量一直没跑。这次补跑 562 项，失败 3 项：两个是 Codenames 移动端的布局用例，一个是沉船动画（单独复跑通过，是并发下的老问题）。

两个 Codenames 用例是真回归，而且是我在 **I18N.2 汉化时引入的**：

```diff
- aria-label={`\${team} team`}          // team 是小写 "blue" → "blue team"
+ aria-label={t("board.codenames.teamLabel", { team: name })}   // name 是 "Blue" → "Blue team"
```

`ui-polish` 和 `identity-layout` 两个用例用 `getByRole("complementary", { name: "blue team", exact: true })` 定位队伍面板，大小写变了就再也匹配不上，测试超时。修法是给面板单独一份小写队名（英文 `blue`/`red`，中文 `蓝方`/`红方`），可见文案不变。

这条正好说明为什么"只跑相关 spec"不够：汉化不动布局，但动了无障碍名称，而布局用例靠无障碍名称找元素。

## 6. 仍然留着的两笔账

| 项 | 现状 | 为什么不在本轮动 |
| --- | --- | --- |
| Contexto 的 `persist` 拒绝 | 词不在词典时先 `saveState`+`broadcastState` 再返回错误，与幂等回执分两次写 | 行为沿用迁移前；只影响 `lastAttempt`，不消耗猜词次数。修法是把它变成平台的"拒绝也落盘"统一路径，那是一次跨插件的接口改动，不值得在本轮为一条状态付双倍契约风险 |
| Poker 牌堆承诺哈希 | `shuffleDeck` 里 `void sha256Hex(...).then(...)`，哈希在发牌那次持久化之后才写回状态，因此**发牌的那一份状态里 `deckCommitHash` 是 `null`** | 与迁移前逐字一致。新增 `PokerRoom.restart.test.ts` 把窗口钉准：发牌后任一动作的持久化都会带上哈希，从该状态重建的房间读到同一个值，所以暴露窗口只是"发牌到下一次写"这一瞬间。真修需要让开局动作变成异步（契约级改动），复审也建议不要在收尾轮改下注状态机 |

另外，**M3.6–M3.9 四个阶段仍未部署**，线上跑的是 10-30 的 i18n 构建。部署验收（staging → 真人与多 agent 同局 → 归档恢复）是 M3 正式收尾的最后一步，需要真机与外部客户端，不在本轮范围内。
