## 2. `send_action` 文档漂移（先定语义，再改文档）

**事实**（`mcp/createServer.ts:1353-1440`）：

| 场景 | 实际返回 |
| --- | --- |
| 非终局成功 | `{ ok, replayed, acceptedRevision, next }` — **不含 state** |
| 动作结束对局 | `{ ok, terminal: true, reason, finalState, next }` |
| `room_create`/`room_join`/`get_state`/`start_game` | 含 `state` |

代码里 DO 本来返回了 `state`，是 MCP 层**故意丢弃**（注释与 `next: "wait_for_turn"` 一致）：长局每步都带完整状态会放大上下文成本。因此这属于"文档落后于有意的实现"，不是实现缺陷。

**处理**：只改文档，描述三件事——哪些工具带 `state`、`send_action` 的确认态、终局态用 `finalState`，并明确"下一步状态请用 `wait_for_turn`（优先）或 `get_state` 读取，二者都给完整状态而非增量"。**未改任何代码或字段**；若后续决定反过来（让 `send_action` 也返回 `state`），那是加法式契约变更，需要单独评估上下文成本。

## 3. Checkers 迁移

**房间从 307 行降到 126 行**；规则搬到 `games/checkers/`：

```text
games/checkers/rules.ts    88 行   开局摆子、走法生成（强制吃子/连跳锁定/升王）、计数、局面键

```

**金样本覆盖**（`checkers.golden.ts`，20 步 / 7 个拒绝）：

| 场景 | 断言点 |
| --- | --- |
| 开局 | 12/12 子、每方 7 个走法、黑先 |
| 自然对局 6 步 | 棋盘、子数、回合号、双方 `legalActions` |
| 强制连跳 | 第一跳后 `forcedPiece={3,4}`、`legalMoves` 只剩续跳、`turnNumber` 不变；第二跳后换手 |
| 升王 | 落 `(0,1)` 变 `3`，`lastMove.crowned=true`，回合结束 |
| 无合法走法 | 对手无子 → `winner=seat1`、`reason=no_legal_moves` |
| 80 手无进展 | `quietTurns=79` + 王走一步 → `winner="draw"`、`no_progress` |
| 三次重复 | 预置 `positionCounts[key]=2` → 走成同一局面 → `winner="draw"`、`repetition` |
| 回合超时 | 判**对手**胜、`turn_timeout` |
| 对局时钟到期 | `winner="draw"` |
| 拒绝 | 非当前玩家 409、坐标越界/负数/小数/缺字段 400、非法走法 422、未知动作 400 |

**内部计数不外泄**：`positionCounts`（重复局面计数）在公开投影与**回放帧**里都被剥离——旧的 `buildRewatchView` 就是 `projectStateFor("")`。这逼出了 `rewatchView` 钩子（见 §4）。

## 4. 契约的两处扩展（都由 Checkers 强制）

| 扩展 | 原因 | 风险控制 |
| --- | --- | --- |
| `rewatchView?(state)` | 回放帧必须剥离 `positionCounts`；默认"整份 state"会把它写进归档 | 默认行为不变（返回整份 state）；只有显式声明才接管 |
| `GameSeatIdentity.role?` 改为可选 | Checkers 的 `you` **没有** `role` 键（只有 `seat`/`color`），若强行返回 `role:null` 会改变公开投影 | 适配器只合并插件返回的键；Checkers 不返回 `role`，`you` 形状零变化（金样本 `role: null` 来自缺省，`toEqual` 一致） |

`BaseGameRoom.buildRewatchView()` 现在先问 `gameRules()?.rewatchView`，否则返回 state；旧的 `switch (projected.type)` 里 `case "checkers"` 已删除，MCP 决定字段改由 `agentFields` 提供。

## 7. 风险与下一阶段

1. **Checkers 的 `quietTurns` 语义**：只有"王的非吃子移动"会累加，man 走一步会清零——金样本已固化，迁移没有改；但规则说明文字（`GAME_INSTRUCTIONS.checkers`）写的是"80 turns without a capture or man move"，与实现一致，无需改。
2. **`rewatchView` 与 `projectState` 目前都由 Checkers 提供同一份剥离逻辑**：若未来有游戏需要"回放比进行中多揭示"，两个钩子可以分开实现（Codenames 就是这种形状）。
3. **`compactAgentDecisionState` 仍是按 `gameType` 分支**：迁移 Contexto/Pokémon 前应把它收进插件，否则新游戏的紧凑决定态只有公共字段。
4. **Battleship 需要确定性舰队**：金样本必须能固定随机布阵，否则等价性不可比；建议先给 `randomFleet()` 注入种子或在测试里预置双方舰队。
5. **e2e 未运行**：需要本地 dev server 与浏览器。

**建议顺序**：Battleship（首个真正用上 `mayActNow` + `projectState` 的游戏）→ Codenames（补齐 `validateStart` 等 3 个钩子）→ 把紧凑决定态收进插件 → 再评估方案 B（通用 DO）。
