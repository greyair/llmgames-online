## 1. 结论

Battleship 已迁到插件契约，**没有为它新增协作机制**：并发布阵用 M3.3 的 `mayActNow`，私有舰队用已有的 `projectState`，回放揭盘用 M3.4 的 `rewatchView`，布阵超时用 `onTurnTimeout`。只补了两个小幅扩展（§4），它们都是"Battleship 的公开视图本来就没有这个键"造成的，不是新架构。

房间类 **1611 → 125 行**，规则拆成 4 个模块；等价性由**迁移前采集的金样本**逐字段证明：

| 维度 | 覆盖 |
| --- | --- |
| 步骤 | 17 步 × 3 个房间（常规对局 / 布阵超时 / 终局） |
| 双方私有视图 | 每步各记录 p1、p2 的 `you` / `yourBoard` / `opponent` / `stats` / `shotLog` |
| Agent 决定态 | 每步各记录一份完整 MCP 视图（`ownGrid` / `targetGrid` / `fleet` …） |
| 旁观视图 | 每步一份双盲投影（两块棋盘都不得出现 `cells`） |
| 拒绝 | 15 条，逐条比对状态码与英文文案 |
| 事件 | 67 条审计事件的类型与载荷顺序 |
| 回放 | 终局回放文档（`revealedShips` / `revealedMines`） |

**结果：迁移后与旧实现完全一致**（唯一差异是 `you` 里键的插入顺序，JSON 语义无关）。

## 3. 金样本是怎么保证"可信"的

### 3.1 确定性

生产随机性**完全没动**：`randomInt` / `randomId` 仍是 CSPRNG，`randomFleet()` 仍随机布阵。测试侧用 `vi.spyOn(crypto, "getRandomValues")` 填零，把座位抽签、超时自动布阵、水雷反击三处随机固定下来。

`withSeededRandom()` 只在测试文件中调用，`pnpm test` 之外的任何代码路径都不会走到它。

### 3.2 只记录规则产出

金样本丢弃了平台自有字段：房间 `id` / `roomCode` / 生命周期时间戳、`gameTimeRemaining` / `turnTimeRemaining` / `startedAt`、以及每发炮弹的 `salvoId`（随机 UUID）。

`salvoId` 的丢弃是有取值的：齐射分组信息仍然通过 `sequence` + `weapon` 保留，只是不再把随机串写进夹具。

### 3.3 采集脚本就是比对脚本

`battleshipScenario.ts` 是**同一份**脚本：采集时驱动旧房间，比对时驱动新房间。所以等价性失败一定意味着规则变了，而不是两个测试各写了一套。

需要重新采样时：`BATTLESHIP_CAPTURE=1 pnpm --filter @llmgames/workers test`（默认跳过，避免测试写文件）。

## 4. 迁移逼出的两个扩展

都不是提前设计的，是被"公开视图必须逐字节不变"逼出来的：

| 扩展 | 原因 | 影响面 |
| --- | --- | --- |
| `youFields?(state, playerId, viewer)` | Battleship 的 `you` 有 `ready` / `munitionPoints` / `weapons` / `weaponCosts`，而 `seatIdentity` 只描述身份 | 只有声明它的游戏生效；Codenames 的 `team` / `canSeeKey` 可直接复用 |
| `GameSeatIdentity.seat` 改为可选 | Battleship 的 `you` **从来没有** `seat` 键，强行返回 `null` 会改变公开形状 | Connect4 / Reversi / Checkers 仍返回 `seat`，投影零变化 |

## 5. 顺带修掉的一处旧缺陷

旧 `finishAttackTurn` 在终局时执行：

```ts
void this.saveState().then(() => this.broadcastProjected("game_ended", …));
```

这正是 M3.2.1 在 Connect4 上修掉的"提前落盘"模式——终局状态先写一次，再靠 `dispatchAction` 写第二次；若第二次（含幂等回执）失败，磁盘上就会留下"已结束但无法重放"的残局。

迁移后它变成 `{ stop_timers } + { event: game_ended } + { match_ended }` 三个效果，由平台在回执写入成功后统一广播。Battleship 因此**不再有这条路径**。

## 7. 剩余风险

1. **`compactAgentDecisionState` 仍按 `gameType` 分支**（`packages/game-catalog/src/agent-state.ts`）。Battleship 的 `wait_for_turn` 仍走该分支，而不是插件的 `agentFields`；两条路径目前输出一致（金样本覆盖了 `agentFields`，`rules.test.ts` 覆盖了 compact 路径），但长期是重复实现。建议在 Codenames 迁移时一并收口。
2. **首发玩家抽签在插件里重算了一次**。`beginBattle` 发生在动作里（双方都布好阵之后），插件无法调用平台的 `startingPlayerIndex()`，因此按同一规则本地实现：有系列赛用 `series.firstPlayerId`，否则 `randomInt(players.length)`。平台若改这套规则，插件会滞后。已在 `actions.ts` 注释标注。
3. **布阵超时的自动布阵仍用 CSPRNG**。这是产品行为（玩家不出现时服务端替他布阵），迁移未改变其随机性；但意味着"同一房间两次超时"结果不同，重放只能依赖已记录的 `ships` 快照。
4. **`rewatchView` 总是揭盘**，包括对局进行中调用时。当前只有 `game_ended` 与归档会读取它（已核对调用点），但若将来新增"对局中预览回放"的入口，必须显式限制。
5. **远程 MCP 全链路**（`gameJourney.test.ts`）仍只覆盖 Connect4。Battleship 的 MCP 路径由 `rules.test.ts` 的 `compactAgentDecisionState` 断言与金样本的 `agent` 字段共同覆盖，但没有端到端跑一局。
