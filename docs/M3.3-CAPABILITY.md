# M3.3 能力验证：多阶段、并发决策与角色私有状态

- **基线**：`ced26c5`（M3.1/M3.2 实现），本轮 M3.2.1 + M3.3 在其上增量
- **验证方式**：读 `BaseGameRoom` 的实际覆写点 + 迁移 Reversi 实测 + 夹具实测 `mayActNow`
- **结论摘要**：Reversi 只逼出 2 个契约扩展（`onMatchTimeout`、座位 `color`）；Battleship/Codenames 还需要 2 个钩子（`validateStart`、`decisionReadyAt`）、1 组座位字段（`team`/`canSeeKey`）和 1 个大厅特例决策

## 1. 契约现状（M3.3 后）

```ts
interface GamePlugin<TState, TId> {
  id; minPlayersToStart; initialTurnPhase;
  createInitialState(config, roomCode, now): TState;
  start(state, { firstPlayerIndex, now }): void;
  turnActions(state, playerId, { isSpectator }): readonly string[];
  mayActNow?(state, playerId): boolean;              // M3.3 新增
  seatIdentity(state, playerId, viewer): { seat, role, color? };
  applyAction(state, playerId, intent, now): GameActionResult;
  onTurnTimeout?(state, playerId, now): readonly GameEffect[];
  onMatchTimeout?(state): void;                      // M3.3 新增
  projectState?(state, playerId): object;
  agentFields?(projection): WireObject;              // M3.2.1 收紧：只接收收件人投影
}
```

`mayActNow` 由平台单点消费：`BaseGameRoom.isYourTurn`（`:2104`）。它同时决定投影里的 `you.isYourTurn`、`wait_for_turn` 的放行、系列赛指标计时与 `resolveTurnWaiters`，因此接一个钩子即可覆盖并发决策的全部入口。

## 2. Reversi（已迁移，实测）

| 需求 | 旧实现 | 结果 |
| --- | --- | --- |
| 自动跳过（对手无合法手） | `advanceAfterMove` 内分支 | ✅ `applyAction` 内部处理，`lastPass` 落状态，事件 `turn_passed` |
| 连续回合（双方都只有一方能动） | 同上 | ✅ 同一 `advanceTurn`，`currentPlayerId` 回到原玩家 |
| 终局（双方都无手） | `finishByScore` → `recordEvent` + `saveState` + `broadcastProjected` | ✅ 返回 `stop_timers` + `game_ended` + `match_ended`，平台原子写后广播 |
| 回合超时按跳过规则走 | `onTurnTimeout` 覆写 | ✅ `onTurnTimeout(state, playerId, now)`，超时路径**不**记 `turn_passed`（与原实现一致） |
| 对局时钟到期按子数判胜 | `onGameTimeout` 覆写 | ⚠️ 契约原先没有钩子 → **新增 `onMatchTimeout(state)`**（`settleExpiredTimers` 已在调用后统一收尾） |
| 座位显示色（黑/白） | `buildYouContext` 里 `color` 与 `role` 同名 | ⚠️ `GameSeatIdentity` 原只有 `seat`/`role` → **新增可选 `color`** |

Reversi 没有隐藏信息，因此不需要 `projectState`；`agentFields` 提供 `board/seats/scores/legalMoves/lastMove/lastPass`，与旧 `buildAgentView` 分支逐字段一致（金样本 + `check:ai-spec` 双重验证）。

## 3. Battleship（未迁移，按代码逐项对照）

| 能力 | 现有代码证据 | 契约能否表达 |
| --- | --- | --- |
| 多阶段 placement → battle | `initialTurnPhase: "placement"`（`BattleshipRoom.ts:358`）、`turnState.phase` 由房间推进 | ✅ `initialTurnPhase` + `applyAction` 自行改 `phase` |
| **并发布阵（两人同时决策）** | `isYourTurn` 覆写：placement 阶段看 `!board.ready`（`:803-820`） | ✅ `mayActNow`（本轮已实现并夹具验证） |
| 布阵超时自动部署并开战 | `onTurnTimeout` placement 分支：随机舰队 → `beginBattle()` → `saveState` + `broadcastState`（`:318-355`） | ✅ `onTurnTimeout` 改 state 并返回事件；adapter 用 `settleRuleTimeout()` 落盘并广播 |
| 命中续turn、未中换手、能量结算 | `handleGameAction` 内 | ✅ `applyAction` 决定 `turnState` |
| 私有舰队 / 雷达公告 | `projectStateFor` 覆写（`:780-801`） | ✅ `projectState` |
| 全量回放（揭示双方舰队） | 未覆写 `buildRewatchView`，用默认"整份 state" | ✅ 默认即全量揭示，无需钩子 |
| 开局前校验 | 未覆写 `validateStartGame` | ✅ 不需要 |

**Battleship 结论**：`mayActNow` + `onTurnTimeout` + `projectState` 足够，不需要新钩子。迁移成本主要在 1 611 行规则搬运与等价性金样本（布阵随机、需注入确定性舰队）。

## 4. Codenames（未迁移，按代码逐项对照）

| 能力 | 现有代码证据 | 契约能否表达 |
| --- | --- | --- |
| 队长私有 key、未翻开牌 `null` | `projectStateFor`（`:292-300`） | ✅ `projectState` |
| 队伍 + 角色决定谁能行动 | `isYourTurn` 按 `activeTeam` + `phase`（`clue`→spymaster，`guess`→operative）（`:323-333`） | ✅ `mayActNow` |
| 同一阶段多名 operative 都可猜 | 同上（返回 true 给全队 operative） | ✅ `mayActNow`（并发的另一种形态） |
| 阶段化动作集（给线索 / 猜词 / 停猜） | `getLegalActions`（`:334-357`） | ✅ `turnActions`（插件可读 assignments 自行判断） |
| `you.team` / `you.role` / `you.canSeeKey` | `buildYouContext`（`:358-371`） | ⚠️ **缺口**：`seatIdentity` 目前只有 `seat`/`role`/`color`；需要 `team`/`canSeeKey`（或等价的声明式扩展） |
| 开局前校验（每队 1 队长、至少 1 队员、人数差 ≤1） | `validateStartGame`（`:396`）→ `validateCodenamesAssignments` | ⚠️ **缺口**：契约没有 `validateStart(state)` |
| 大厅内改角色（含旁观者占座） | 平台在 `dispatchAction` 用 `isCodenamesRoleJoin` 特例放行旁观者（`BaseGameRoom.ts:3042-3056`） | ⚠️ **缺口**：要么保留该平台特例（可接受，但要写进契约文档），要么加"大厅动作/旁观者可行动"钩子 |
| 成员变旁观者时清空角色 | `onRoomMemberRoleChanged`（`:306`） | ⚠️ **缺口**：契约没有成员角色变更钩子（只影响大厅） |
| 全量回放 | `buildRewatchView` override 返回整份 state（`:301-303`），与默认相同 | ✅ 无需钩子（该覆写是冗余的） |

**Codenames 结论**：需要 `validateStart`、座位 `team`/`canSeeKey`、成员角色变更钩子；大厅角色动作建议保留平台特例并在文档中固定（它发生在"对局开始前"，不属于任何一局的规则）。

## 4.1 Checkers（M3.4 已迁移，实测）

## 6. 判断：现在不要再加抽象

本轮只加了两处**有实测场景**的钩子（`mayActNow` 有夹具验证，`onMatchTimeout` 由 Reversi 强制），其余缺口全部**留到对应游戏迁移时**再加，并用同一条等价性金样本流程验证。理由：

1. 每加一个钩子就多一条需要回归的路径（`wait_for_turn`、系列赛指标、投影、超时）。
2. `validateStart`、`decisionReadyAt`、成员角色钩子都只服务**一个**游戏，提前抽象等于为未来猜测付费。
3. 方案 B（通用 DO）仍未验证，契约继续膨胀只会提高那次切换的成本。
