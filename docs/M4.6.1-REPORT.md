# M4.6.1 — 浏览器卡在大厅：前端运行时契约没跟上新游戏

- **报告日期**：2026-11-01
- **触发**：线上 16 款游戏上线后，新开的三款游戏（飞行棋 / 跑得快 / 斗地主）停在等待大厅，服务端已经开局
- **结论**：前端 `clientViewSchema` 拒绝新游戏的状态帧，`Room.tsx` 把被拒的帧静默丢弃，React 保留上一帧，所以画面停在开局前。只改前端，不需要迁移 D1 或重发 Durable Object。

## 1. 根因

浏览器收到的每一帧都要过 `apps/web/src/domain/game-state.ts` 的 `clientViewSchema`，失败就 `return`：

```text
Room.tsx  receive()
  clientViewSchema.safeParse(value).data  → null
  → return             // 不 setState，不报错
```

这个 zod 契约是手写的，与服务端的 `buildClientView()` 靠人工同步。M4 新增八款游戏时同步了 TypeScript 类型，**没有同步运行时 zod**，于是两处对不上：

| 字段 | 服务端实际下发 | 旧运行时契约 | 结果 |
| --- | --- | --- | --- |
| `you.role` | `seat0`、`seat1`、`seat2`（飞行棋/跑得快/斗地主/大富翁） | 只接受 `player1`/`player2`/`black`/`white`/`player`/`captain`/`spymaster`/`operative`/`spectator` | 拒绝 |
| `you.role` | `red`（中国象棋红方） | 同上，没有 `red` | 拒绝 |
| `board` | 64 字符 FEN 字符串（国际象棋） | 只接受 `number[][]` 或词卡数组 | 拒绝 |
| `board` | 90 格 `string[]`（中国象棋） | 同上 | 拒绝 |

`ClientView` 的 TypeScript 类型里 `board` 早就写了 `string | string[]`，注释还写明"国际象棋一个 64 字符串、中国象棋 90 格"——类型放宽了，校验器没放宽，**类型在这里是假的**。

## 2. 为什么测试没发现

- 规则测试、房间测试、MCP 全链路都在服务端跑，服务端不读这个 zod。
- `boardRegistry` 测试只断言组件注册过。
- 四视口布局门禁走 `dev/preview` 夹具，夹具直接喂给组件，不经过 `Room.tsx` 的 `receive()`。
- 旧的 `view-contracts.test.ts` 只列了旧游戏的角色。

三层各自正确，中间那条"服务端帧 → 前端契约"没有任何测试。

## 3. 修复

### 3.1 角色

```ts
const viewerRoleSchema = z.union([
  z.enum(["player1", "player2", "black", "white", "red", "player",
          "captain", "spymaster", "operative", "spectator"]),
  z.string().regex(/^seat(?:[0-9]|1[0-1])$/),
]);
```

座位角色收成受控格式，而不是放开成 `z.string()`：`seat12`、`reds`、`administrator` 仍然被拒。

### 3.2 棋盘

```ts
board: z.union([
  numericBoardSchema,
  wordBoardSchema,
  z.string().length(64),          // 国际象棋 FEN 序
  z.array(z.string()).length(90), // 中国象棋 90 个点
]).optional(),
```

长度写死而不是 `z.string()`：字符串棋盘只有这两款会发，长度不对就是真错。

### 3.3 不再静默丢帧

`Room.tsx` 把被拒的帧报告一次（每个连接一次），只打印**字段路径与错误码**，不打印帧内容——帧里可能有手牌：

```text
Dropped a game state frame the client contract does not model:
you.role (invalid_union), board (invalid_union)
```

为此把 `clientViewContract`（`z.custom` 里面那个严格对象）导出，否则外层包装的报错没有 path。

## 4. 新增门禁

`apps/workers/src/tests/contracts/browserViewContract.test.ts`（21 条）：

- 用 `createGameRoomFixture` 真实开局，取 `buildClientView()` 的实际输出——就是发到 socket 的那份——对 16 款游戏**每一个座位**跑 `clientViewContract`。
- 对高危游戏额外断言 `you.role` 的形态（`seat0`/`red` 等），防止夹具哪天改成大厅帧后测试假通过。
- 单独断言国际象棋棋盘 64 长度、中国象棋 90 长度。
- 负例：`seat12`、`reds`、`administrator` 被拒；64/90 以外的棋盘被拒。

这个文件跨包引用了 `apps/web/src/domain/game-state.ts`，是刻意的：契约的定义方是前端，验证方必须在服务端产出帧的地方。`pnpm --filter @llmgames/workers lint` 同时校验两边类型。

`docs/adding-a-game.md` 的验收清单加了这一条：新游戏的每个视角必须通过 `clientViewSchema`，并把用例加进上面这个文件。

## 5. 影响面

同一个 bug 还顺带坏了**回放**：`features/replay/rewatchPayload.ts` 也用 `clientViewSchema` 校验归档帧，所以新游戏的战绩回放同样会空。修完后两条路径一起恢复。

## 8. 没验到的

**没有在线上真开一局。** 创建房间需要 OAuth 交互授权，脚本跑不了。修复的正确性由"真实 `buildClientView()` 输出 → 契约"这条用例保证，但"浏览器里点一下真的进棋盘"仍未人工确认。这条缺口和 M4 发布记录第 6 节是同一个。

建议下一次登录线上时，按顺序点：飞行棋（2 人）→ 跑得快（3 人）→ 斗地主（3 人）→ 国际象棋 → 中国象棋，各看一眼是否进入棋盘、手牌/棋盘是否正常，并顺手看一局新游戏的战绩回放。
