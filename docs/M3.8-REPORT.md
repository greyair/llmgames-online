# M3.8 — Pokémon 迁移与「密封双选」验证

- **基线**：`f60c295`（M3.7 完成）
- **范围**：仅迁移 Pokémon，不改协议、不加新钩子
- **结论**：迁移完成；既有 15 个用例不改一行全部通过，7 款游戏（除 Poker）都已走通 MCP 全链路

## 1. 结论

Pokémon 是这轮迁移里最难的一款：**一个回合不是一次意图，而是两个密封选择同时提交后由模拟器统一结算**。它的三个特点分别踩在契约的不同角落：

| 特点 | 契约落点 |
| --- | --- |
| 两个座位同时决策、谁先交都行 | `mayActNow` 逐座位回答，`turnState.currentPlayerId` 全程 `null` |
| 选择未结算前公开，但不得泄露对手未提交的选择 | `projectState` 逐接收者构造视图 |
| 战斗本体是 `@pkmn/sim` 的复杂对象 | 只以 `battleSnapshot` JSON 持久化，规则层解析→操作→回写 |

**没有新增任何钩子**。M3.3 加的 `mayActNow`、M3.6 加的 `projectState` 已经够用，这也回答了设计时的一个疑问：密封同时行动不需要单独的 `simultaneous` 钩子。

迁移后 `PokemonRoom.ts` 从 **236 行降到 99 行**。

## 3. 两个实现决策

**① 快照解析缓存放在规则层，键是快照本身。** 每次构建视图、每次校验合法性都要把 JSON 变回 `Battle`，而一次广播会对每个接收者各构建一次视图。规则层用"最后一个快照 → 已解析战斗"的单条记忆化：快照字符串唯一决定战斗内容，因此缓存不会把 A 房间的战斗答案给到 B 房间。这不是实例状态，插件可以保持无状态。

**② 结算时机由"回合号或请求是否变化"判定。** 座位提交后战斗可能还没结算（等对手），此时不能重置决策时钟；只有真正推进（`battle.turn` 或 `requestState` 变化）才重置。这段逻辑与迁移前逐行一致，也是 15 个既有用例里"密封回合在存储重载后继续"能过的原因。

## 5. 剩余风险

1. **`battleSnapshot` 的兼容窗口**。快照是 `@pkmn/sim` 的私有 JSON 形态，升大版本可能读不了旧快照。迁移没有改变这一点（之前也是存 JSON），但值得在依赖升级流程里写明：升级 sim 前先排空在途房间。
2. **单条记忆化在并发房间下命中率低**。两个房间交替构建视图会互相顶掉缓存；正确性不受影响，只是白解析。若压测发现视图构建成为瓶颈，可换成小容量 LRU，但要把"快照决定内容"这条不变量保留下来。
3. **回放仍是全量揭示**（`battleView(battle, null, true)`），归档里含双方完整队伍。符合约定，但同样需要在归档文档里写清。
4. **Poker 是最后一款未迁移的游戏**，也是最大的一款（1,227 行、边池、5 秒结果窗口）。它需要的钩子可能不止现有这些。
