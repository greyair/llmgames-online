## 2. M3.2.1-1：`match_ended` 不再提前落盘

**缺陷**：`applyGameEffects` 在 `handleGameAction` 内部执行 `void this.saveState().then(broadcast)`。此时 `dispatchAction` 还没写"状态 + 回执"的配对写入，于是：

1. 一次制胜行动产生 **两次** `gameState` 写入；
2. 若第二次（回执）写入失败，磁盘上已经是 `ended` 状态却没有回执 → 重启后是一局"无法重放、也无法重试"的终局；
3. 提前的 `saveState()` 是未 await 的 Promise，写入失败会变成 unhandled rejection。

**修复**：

- `match_ended` 只登记 `pendingMatchEnd`（同时停表），不写存储；
- `dispatchAction` 在 `saveAppliedAction`（状态 + 回执的单次写入）成功后，才调用 `deliverPendingMatchEnd()` 广播 `game_ended`；
- 超时路径新增 `flushPendingMatchEnd()`：先落盘再广播；插件适配器统一走 `settleRuleTimeout()`。

**测试**（`BaseGameRoom.matchEnd.test.ts`）：

| 用例 | 断言 |
| --- | --- |
| 终局与回执同一次写入 | 重启后状态为 `ended`，同一 `requestId` 重试返回 `replayed: true` 且不重复落子 |
| 回执写入失败不留终局残影 | 注入 `ackedActionRecords` 写失败 → HTTP 500、内存回滚、重启后仍是 `playing` 且制胜子不在盘上；解除故障后同一 `requestId` 只生效一次 |

> 该用例在修复前会失败：旧实现先写终局、后写回执，重启后读到 `ended` 而重试被拒。

## 3. M3.2.1-2：`agentFields` 只接收收件人投影

**缺陷**：`agentFields(state)` 拿到的是**原始 state**，插件可以（无意或有意）把对手私有字段塞进 MCP 响应，绕过 `projectState` 建立的边界。

**修复**：

- 契约签名改为 `agentFields(projection: WireObject)`，平台传入本收件人的投影；
- 平台保留键（`type`/`status`/`players`/`roomMembers`/`gameTimeRemaining`/`turnState`/`winner`/`you`/`series`）在合并时被丢弃，插件无法改写身份、名册、时钟、回合与结果。

**测试**（`pluginAgentFields.test.ts`）：用一个"故意越权"的插件（`{...projection, type:"spoofed", players:[], you:{playerId:"attacker"} }`）驱动两席对局，断言：

- `type/status/players/winner/you` 仍是平台值；
- 每席只看到自己的隐藏数字，对手的键根本不存在；
- 序列化结果不含 `spoofed` / `attacker`。

## 4. M3.3-3：Reversi 迁移

方法与 Connect4 一致：**先抓金样本，再迁移**。

- 金样本：`reversi.golden.ts`（854 行）—— 开局 8×8 棋盘、6 步自然对局、8 个拒绝场景（非当前玩家 / 出界 / 负数 / 小数 / 缺字段 / 已占格 / 不成夹 / 未知动作）、强制造型盘上的"跳过 + 连续回合"、按子数终局、对局时钟到期按子数判胜。
- 比对字段：棋盘、子数、状态、阶段、回合号、当前座位、胜负、合法着法、`lastMove`、`lastPass`、双方 `role`/`color`/`legalActions`、拒绝的 HTTP 状态与 `code`/`message`/`category`/`recovery`。
- 房间从 **432 行降到 123 行**；规则在 `games/reversi/{rules,plugin}.ts`（105 + 285 行），`ReversiRoom` 继续 re-export 原有工具函数，外部导入不变。
- `BaseGameRoom.buildAgentView` 的 `case "reversi"` 已删除，MCP 决定字段改由插件提供；`check:ai-spec` 无 diff。

**Reversi 逼出的两处契约扩展**（均有实测场景，非预判）：

| 扩展 | 原因 |
| --- | --- |
| `onMatchTimeout?(state)` | 对局时钟到期要按盘数判胜，而平台默认只收尾、不留结果 |
| `GameSeatIdentity.color?` | 旧 `you.color` 与 `you.role` 同名但客户端都读，契约原先只有 `role` |
| `onTurnTimeout(state, playerId, now)` | 规则不再自己读时钟（`now` 由平台给），与 `applyAction` 一致 |

## 5. M3.3-4：多阶段与并发决策能力

结论写在 `docs/M3.3-CAPABILITY.md`，要点：

- **新增 `mayActNow?(state, playerId)`**，平台在 `BaseGameRoom.isYourTurn` 单点消费，因此 `wait_for_turn`、投影的 `isYourTurn`、系列赛计时、回合唤醒全部一致。
- 实测（`concurrentDecision.test.ts`）：把插件放宽为"两席都可行动"后，两席 `you.isYourTurn` 均为 true，且两人 `wait_for_turn` 都**立即**以 `your_turn` 返回；未放宽的游戏仍是单人等待（对照组）。
- **Battleship**：`mayActNow` + `onTurnTimeout` + `projectState` 已足够，无需新钩子（证据：`BattleshipRoom.isYourTurn:803`、`:318-355`、`:780-801`）。
- **Codenames**：还需 `validateStart`、座位 `team`/`canSeeKey`、成员角色变更钩子；大厅内的 `assign_codenames_role` 目前是平台特例（`BaseGameRoom:3042-3056`），建议保留并在文档固定。
- 其余缺口（Poker 的 `decisionReadyAt`、认输、`lastAnnouncement` 的 code 化）继续留到对应游戏迁移时再加，理由写在能力文档 §6。

## 6. M3.3-5：真实 MCP + 归档全链路

`apps/workers/src/tests/mcp/gameJourney.test.ts` 走**完整产品路径**，Worker 内部零桩：

```text
agent_claim ×2 → room_create → room_join → start_game
→ send_action(drop_disc) ×7（每步 get_state 读回）
→ 两席 get_state 结束投递 → R2 归档 + D1 索引
→ gzip 解压 → gameLogDocumentSchema 解析 → 校验回放帧
```

断言覆盖：

| 关注点 | 断言 |
| --- | --- |
| MCP 工具链 | 两个独立 controller 各自 seated；`roomId === connect4-<roomCode>`；动作全部 `isError: false` |
| 结束状态 | 最终 `get_state` 为 `ended`，`you.legalActions` 不再含 `drop_disc` |
| 归档契约 | R2 对象可被 `gameLogDocumentSchema` 解析；`gameType: connect4`、`endReason: connect4`、参与者 `p1`/`p2` 且 `isAgent: true` |
| 事件完整性 | 首事件 `game_started`、7 次 `drop_disc`、6 次 `turn_changed`、含 `game_ended`、末事件 `action` |
| 回放 | 帧数 > 1，末帧 `status: "ended"`，帧内棋盘底行前四格为 `[1,1,1,1]`（胜线） |
| 隐私 | 归档原文不含任何 controllerId、不含 `agentId` |
| D1 索引 | `game_logs` 行与文档一致（`game_type`/`end_reason`/`event_count`/`r2_key`） |

**发现的文档漂移（未改代码）**：`MCP_STATE_CONTRACTS.md` 称成功的 `send_action` 响应包含 `state`，实际实现返回 `{ ok, replayed, acceptedRevision, next }`，状态需再调 `get_state`/`wait_for_turn`。测试按实际行为编写。建议后续统一（要么补字段，要么改文档），本轮不动公开契约。

1. **`send_action` 与文档不一致**（见 §6）：M4 托管 Agent 会踩，建议作为下一轮第一项。

6. **e2e/Playwright 未执行**：需要本地 dev server 与浏览器，本轮未启动。
